# SPEX — دليل النشر للإنتاج

هذا الدليل يغطي تجهيز قاعدة البيانات (Neon) ونشر المنصة (Railway أو Render) خطوة بخطوة.

---

## 0. ما تغيّر في هذا الإصدار

- مصادقة حقيقية من الخادم (bcrypt + جلسات JWT في كوكيز `httpOnly`)، لا مقارنة كلمة مرور في المتصفح ولا "كلمة مرور رئيسية"
- قاعدة بيانات Postgres حقيقية عبر Prisma بدل ملف `data_store.json`
- كل الـ API محمي بالمصادقة، وكلمات المرور لا تُرسل للعميل أبداً
- خادم إنتاج مستقل (`src/server/index.ts`) يقدّم الواجهة + الـ API معاً على نفس النطاق
- استرجاع كلمة مرور حقيقي عبر بريد إلكتروني فعلي (رمز صالح لمرة واحدة لمدة 30 دقيقة)
- Migration أولى جاهزة في `prisma/migrations/` (لا حاجة لتوليدها يدوياً)، و`prisma/seed.ts` ينشئ حساب SUPER_ADMIN تلقائياً عند الإقلاع إن عرّفت `SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD`
- `render.yaml` جاهز للنشر المباشر على Render عبر Blueprint (راجع القسم 8)

---

## 1. إنشاء قاعدة بيانات Postgres مجانية على Neon

1. أنشئ حساباً على [neon.tech](https://neon.tech) (مجاني).
2. أنشئ مشروعاً جديداً (Project) → سيولّد لك قاعدة بيانات Postgres فوراً.
3. من لوحة التحكم، انسخ **Connection String** (يبدأ بـ `postgresql://...` وينتهي بـ `?sslmode=require`).
4. احتفظ به جانباً — هذا هو `DATABASE_URL`.

> بديل: Supabase يعمل بنفس الطريقة تقريباً إن كنت تفضله.

---

## 2. تجهيز متغيرات البيئة محلياً

```bash
cp .env.example .env
```

عدّل `.env`:
- `DATABASE_URL` = رابط Neon الذي نسخته
- `JWT_SECRET` = مفتاح عشوائي طويل، ولّده بالأمر:
  ```bash
  openssl rand -base64 48
  ```
- `GEMINI_API_KEY` = مفتاح Gemini الخاص بالمنصة (اختياري إن كان كل مستخدم يضيف مفتاحه)
- `RESEND_API_KEY` = مفتاح إرسال البريد الإلكتروني (انظر القسم التالي)
- `APP_URL` = الرابط العلني للمنصة (مثال: `https://spex-yourschool.up.railway.app`) — يُستخدم لبناء رابط إعادة تعيين كلمة المرور داخل البريد

---

## 2.1 تفعيل استرجاع كلمة المرور عبر البريد الإلكتروني (Resend)

1. أنشئ حساباً مجانياً على [resend.com](https://resend.com) (الخطة المجانية تكفي حتى 3000 بريد شهرياً).
2. من لوحة التحكم → **API Keys** → أنشئ مفتاحاً جديداً، وضعه في `RESEND_API_KEY`.
3. للتجربة السريعة، يمكنك ترك `EMAIL_FROM="SPEX <onboarding@resend.dev>"` كما هو (يعمل فوراً بدون إعداد إضافي، لكن الرسائل قد تُصنَّف أحياناً كسبام).
4. **للإنتاج الجدّي**: من تبويب **Domains** في Resend، أضف نطاقك الخاص (مثال `spex.dz`) واتبع تعليمات إضافة سجلات DNS (SPF/DKIM) التي تعرضها، ثم غيّر `EMAIL_FROM` إلى `SPEX <no-reply@spex.dz>`.
5. بدون `RESEND_API_KEY`، الميزة تبقى معطّلة بأمان: الخادم يسجّل تحذيراً في السجلات (logs) ولا يُرسل بريداً، لكن لا يكشف هذا للمستخدم (تُعرض دائماً رسالة نجاح عامة لتفادي تسريب معلومة وجود الحساب من عدمه).

## 3. تثبيت الاعتماديات وتوليد الجداول

مخطط قاعدة البيانات الأول (`prisma/migrations/20250101000000_init`) موجود بالفعل في المستودع،
لذا لا حاجة لتوليده من الصفر. فقط ثبّت الاعتماديات وطبّق المخطط على قاعدة Neon الخاصة بك:

```bash
npm install
npx prisma migrate deploy
```

هذا الأمر ينشئ جداول Postgres الفعلية (User, LessonPlan, ...) حسب `prisma/schema.prisma`،
ثم (عند تشغيل `npm start` لاحقاً) يُنشئ حساب SUPER_ADMIN تلقائياً إن كنت قد عرّفت
`SUPER_ADMIN_EMAIL` و`SUPER_ADMIN_PASSWORD` — راجع القسم 5 أدناه.

للتأكد بصرياً من الجداول:
```bash
npx prisma studio
```

> إن عدّلت `prisma/schema.prisma` لاحقاً (إضافة حقل/جدول جديد)، أنشئ Migration جديدة محلياً بـ:
> ```bash
> npx prisma migrate dev --name وصف_التعديل
> ```
> سيُنشئ هذا مجلداً جديداً داخل `prisma/migrations/` يجب رفعه إلى Git، وسيُطبَّق تلقائياً
> في الإنتاج عبر `prisma migrate deploy` (المُدرَج ضمن أمر `npm start`).

## 4. (اختياري) ترحيل بيانات حقيقية من النسخة القديمة

إن كان لديك `data_store.json` من الخادم القديم يحتوي مستخدمين/بيانات حقيقية:

1. انسخه إلى جذر المشروع (بجانب `package.json`).
2. شغّل:
   ```bash
   npm run db:seed-from-json
   ```
3. سيُشفَّر أي كلمة مرور نص عادي تلقائياً أثناء الترحيل.
4. **احذف الملف بعد التأكد من النجاح** ولا ترفعه إلى Git (مستثنى أصلاً في `.gitignore`).

## 5. إنشاء أول حساب مشرف (SUPER_ADMIN)

بما أن المنصة لم تعد تسمح بالتسجيل الذاتي، وتحتاج حساب admin واحد على الأقل موجود مسبقاً لإنشاء بقية الحسابات، أنشئه بإحدى الطرق التالية (الطريقة الأولى هي الموصى بها لأنها لا تحتاج أي تدخل يدوي):

### الطريقة الموصى بها: إنشاء تلقائي عبر `prisma/seed.ts`

1. في متغيرات البيئة (`.env` محلياً، أو تبويب Environment على Render/Railway)، عرّف:
   ```
   SUPER_ADMIN_EMAIL="admin@example.com"
   SUPER_ADMIN_PASSWORD="كلمة_مرور_قوية_لا_تقل_عن_8_أحرف"
   ```
   (يمكن أيضاً تخصيص `SUPER_ADMIN_FIRST_NAME`, `SUPER_ADMIN_LAST_NAME`, `SUPER_ADMIN_DIRECTORATE_ID`, `SUPER_ADMIN_DISTRICT_ID` — قيمها الافتراضية موجودة في `.env.example`.)
2. شغّل `npm start` (محلياً) أو انشر الخدمة (في الإنتاج) كالمعتاد. أمر `npm start` يشغّل تلقائياً:
   `prisma migrate deploy` ثم `tsx prisma/seed.ts` ثم الخادم — فيُنشأ حساب SUPER_ADMIN
   (بالبريد وكلمة المرور اللذين حدّدتهما، وبـ `role: "admin"`) دون أي خطوة يدوية إضافية.
3. الأمر آمن لإعادة التشغيل: إن كان الحساب موجوداً مسبقاً، لن يُعاد إنشاؤه أو تعديل كلمة مروره أو دوره.
4. سجّل الدخول مباشرة بنفس البريد وكلمة المرور من شاشة الدخول العادية.

إن لم ترغب باستخدام هذه الطريقة (أو نسيت تعريف المتغيرين)، تبقى الطريقتان التاليتان متاحتين كبديل:

### الطريقة أ: إن كان لديك وصول Shell/CLI محلياً أو على منصة الاستضافة

```bash
npx prisma studio
```

في جدول `User`، أضف صفاً يدوياً، مع ملاحظة: حقل `passwordHash` يجب أن يكون **هاش bcrypt**، وليس نصاً عادياً. لتوليده، شغّل مؤقتاً:

```bash
node -e "require('bcryptjs').hash('كلمة_المرور_التي_تريدها', 12).then(console.log)"
```

انسخ الناتج والصقه في حقل `passwordHash`، واملأ `role: "admin"`, `isApprovedByAdmin: true`, `status: "active"`, وبقية الحقول المطلوبة (`username`, `spexId`, `email`, `directorateId`, `districtId`).

### الطريقة ب: بدون Shell إطلاقاً (عبر `bootstrap-admin`، مثل خطط Render المجانية)

بعض الاستضافات المجانية (Render Free مثلاً) لا توفّر تبويب Shell. لهذه الحالة أضفنا مساراً خاصاً في الـ API لإنشاء أول حساب مشرف مباشرة من متصفحك:

1. أضف متغير بيئة `SETUP_SECRET` في لوحة التحكم بقيمة عشوائية طويلة (نفس طريقة `JWT_SECRET`)، واحفظ (سيُعيد نشر الخدمة تلقائياً).
2. افتح موقع منصتك المنشورة في المتصفح.
3. افتح أدوات المطوّر (**F12** أو كليك يمين → Inspect) → تبويب **Console**.
4. الصق هذا الكود، بعد استبدال القيم بين `<>` بمعلوماتك الحقيقية، ثم اضغط Enter:

```js
fetch('/api/auth/bootstrap-admin', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    setupSecret: '<القيمة_التي_وضعتها_في_SETUP_SECRET>',
    email: '<بريدك_الإلكتروني>',
    password: '<كلمة_مرور_قوية_لا_تقل_عن_8_أحرف>',
    firstName: '<اسمك>',
    lastName: '<لقبك>'
  })
}).then(r => r.json()).then(console.log);
```

5. إن ظهرت رسالة نجاح، سجّل الدخول فوراً بنفس البريد وكلمة المرور من شاشة الدخول العادية.
6. **مهم**: هذا المسار يرفض العمل تلقائياً إن وُجد مشرف واحد على الأقل مسبقاً، فهو آمن للاستخدام لمرة واحدة فقط. بعد نجاح الإنشاء، احذف متغير `SETUP_SECRET` من إعدادات الاستضافة لإغلاق هذا الباب نهائياً (اختياري لكن مُستحسن).

بعدها يمكن لهذا الحساب تسجيل الدخول عادياً وإنشاء بقية الحسابات من داخل لوحة التحكم.

## 6. تجربة محلية قبل النشر

```bash
npm run dev
```

جرّب تسجيل الدخول بحساب الـ admin الذي أنشأته، وتأكد أن كل شيء يعمل مع قاعدة بيانات Neon الحقيقية.

## 7. النشر على Railway (الأسهل)

1. ارفع المشروع إلى مستودع GitHub.
2. على [railway.app](https://railway.app): New Project → Deploy from GitHub repo.
3. في تبويب **Variables**، أضف كل متغيرات `.env` (نفس القيم: `DATABASE_URL`, `JWT_SECRET`, `GEMINI_API_KEY`, وأضف `NODE_ENV=production`).
4. في تبويب **Settings → Build**:
   - Build Command: `npm run build`
   - Start Command: `npm start`
5. أمر `npm start` يطبّق مخطط قاعدة البيانات تلقائياً (`prisma migrate deploy`) في كل مرة يُقلع فيها الخادم، فلا حاجة لتشغيل أي أمر يدوي عبر Shell.
6. Railway يوفّر نطاقاً مجانياً بشهادة HTTPS تلقائياً (`*.up.railway.app`). يمكنك ربط نطاق مخصص لاحقاً من نفس الإعدادات.

## 8. النشر على Render (بديل)

### الطريقة الأسرع: Blueprint (`render.yaml`)

المستودع يحتوي ملف `render.yaml` جاهزاً يصف الخدمة بالكامل:

1. على [render.com](https://render.com): **New +** → **Blueprint** → اربط مستودع GitHub الذي يحتوي هذا المشروع.
2. سيكتشف Render ملف `render.yaml` تلقائياً ويعرض عليك الخدمة المُعرَّفة فيه (`spex-platform`) للمراجعة.
3. أدخل القيم المطلوبة يدوياً (المُعلَّمة `sync: false` في الملف): `DATABASE_URL` (رابط Neon)، و`GEMINI_API_KEY` (اختياري)، و`RESEND_API_KEY` (اختياري)، و`SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD` (موصى به لإنشاء أول حساب مشرف تلقائياً — راجع القسم 5).
4. القيم الأخرى (`JWT_SECRET`, `SETUP_SECRET`) تُولَّد عشوائياً وتلقائياً من طرف Render (`generateValue: true`) — لا تحتاج لإدخالها.
5. بعد أول نشر ناجح، حدّث متغير `APP_URL` ليطابق رابط الخدمة الفعلي الذي منحك إياه Render (مثال: `https://spex-platform.onrender.com`)، حتى تعمل روابط إعادة تعيين كلمة المرور بشكل صحيح.
6. أمر `npm start` (المُعرَّف في `render.yaml` كـ `startCommand`) يطبّق مخطط قاعدة البيانات (`prisma migrate deploy`) وينشئ حساب SUPER_ADMIN (`prisma/seed.ts`) تلقائياً عند كل إقلاع، فهذا يعمل حتى على خطة Render المجانية التي لا توفّر تبويب Shell.
7. `render.yaml` يضبط أيضاً `healthCheckPath: /api/health` حتى يتأكد Render أن الخدمة فعلاً جاهزة قبل تحويل الزيارات إليها بعد كل نشر.

### الطريقة اليدوية (بدون Blueprint)

1. New → Web Service → اربط مستودع GitHub.
2. Environment: **Node**.
3. Build Command: `npm ci && npm run build`
4. Start Command: `npm start`
5. أضف نفس متغيرات البيئة الموجودة في `.env.example` يدوياً في تبويب **Environment**.
6. أمر `npm start` يطبّق مخطط قاعدة البيانات تلقائياً (`prisma migrate deploy`) عند كل إقلاع، فهذا يعمل حتى على خطة Render المجانية التي لا توفّر تبويب Shell.
7. Render يوفّر شهادة HTTPS تلقائياً على نطاقه الفرعي المجاني.

> ملاحظة Neon + Render: قاعدة Neon المجانية "تنام" بعد فترة خمول، وأول طلب بعدها قد يستغرق بضع ثوانٍ إضافية لإيقاظها (طبيعي وليس عطلاً). كذلك خطة Render المجانية توقف الخدمة بعد خمول طويل وتعيد تشغيلها عند أول طلب لاحق (أول تحميل بعد الخمول أبطأ من المعتاد).

## 9. نقاط أمان يجب مراجعتها بعد النشر

- [ ] تأكد أن `.env` غير موجود في المستودع (مُستثنى فعلاً في `.gitignore`)
- [ ] `JWT_SECRET` في الإنتاج مختلف عن أي قيمة تجريبية، وطوله 32 حرفاً+
- [ ] `NODE_ENV=production` مضبوط فعلياً (يفعّل `secure` على الكوكيز، أي HTTPS فقط)
- [ ] راجع صلاحيات الحسابات: فقط admin/inspector يمكنهم إنشاء حسابات جديدة، وهذا مطبّق فعلاً في `apiRouter.ts`
- [ ] احذف متغير `SETUP_SECRET` بعد إنشاء حساب المشرف الأول (لم يعد له استخدام، وإبقاؤه لا داعي له) — غير ضروري أصلاً إن استخدمت `SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD`
- [ ] `SUPER_ADMIN_PASSWORD` قوية وفريدة، وليست القيمة التجريبية الموجودة في `.env.example`
- [ ] فعّل النسخ الاحتياطي التلقائي لقاعدة Neon من لوحة تحكمها (متوفر في الخطة المجانية بشكل محدود)

## 10. ما لم يُبنَ بعد (اختياري لمستقبل المشروع)

- **تشفير `customApiKey` في قاعدة البيانات**: حالياً يُخزَّن كنص عادي في عمود مخصص (وليس عبر الواجهة للعميل بعد الحفظ)، وهو مفتاح المستخدم الخاص لا مفتاح المنصة، لكن يمكن تشفيره بمفتاح إضافي (KMS/`crypto`) إن رغبت بمزيد من الصرامة.
- **CSP كاملة (Content-Security-Policy)**: معطّلة حالياً في `helmet` لتفادي كسر الواجهة، يُنصح بضبطها بدقة لاحقاً حسب مصادر السكربتات/الخطوط الفعلية المستخدمة.

> ملاحظة: بعد إضافة نموذج `PasswordResetToken` الجديد لقاعدة البيانات، شغّل `npx prisma migrate dev` (محلياً) ثم `npx prisma migrate deploy` (في الإنتاج) لتطبيق التغيير على الجدول.
